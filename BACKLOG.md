## [вопрос] `interface xraytunN already exists` при старте xray — влияние Lock («Prevent interface removal»)

**Статус:** открытый вопрос. Эмпирическое решение пользователя — снять галку
Lock в Interfaces → Assignments — работает, точный механизм не установлен.

### Симптом

```
Failed to start: app/proxyman/inbound: failed to start proxy > interface xraytun100 already exists
```

xray не может создать TUN-интерфейс: клон с таким именем уже есть в ядре.
Watchdog затем бесконечно перезапускает инстанс с той же ошибкой.

### Что установлено (проверено по исходникам, ноябрь 2026)

1. **FreeBSD `sys/net/if_tuntap.c`** — корневая причина утечек: при смерти
   процесса-держателя `tundtor()` только гасит интерфейс и вычищает адреса,
   **но не уничтожает клон**. Уничтожение — только явный
   `ifconfig <name> destroy`, либо флаг `TUNSTRANSIENT` (ioctl), который
   **xray не ставит**. Любая нечистая смерть xray (SIGKILL, крэш, падение
   старта после создания TUN) оставляет переименованный клон в ядре навсегда.
   Чистый shutdown xray интерфейс уничтожает сам.
2. **OPNsense core ничего не создаёт и не держит**: `cloned_interfaces` —
   0 вхождений в репозитории; `interface_configure()` отсутствующее устройство
   не создаёт (создание только для vlan/bridge/lagg/gre/gif/wlan/tap-модели);
   devd-правило ATTACH в OPNsense пустое; `tap.inc` управляет только
   `tap0N`. Присвоенное имя вида `xraytun100` не матчится даже паттерном
   volatile-устройств `^tun` (начинается с «xray»).
3. **Lock (`interface.lock`)** — чекбокс в Interfaces → Assignments, help
   «Prevent interface removal», **Default=1**. Документированное рантайм-
   поведение: блокирует удаление записи из config.xml и подавляет boot-time
   mismatch prompt для отсутствующего устройства (`console.inc:is_interface_mismatch()`).
   Других рантайм-эффектов в core не найдено.

### Что под вопросом

- Почему у пользователя снятие Lock устранило ошибку старта, если core не
  управляет жизненным циклом tun-клонов. Гипотезы: косвенное влияние на
  порядок config-событий; удаление assignment для unlocked-отсутствующего
  устройства; совпадение по времени (утечённый клон был снесён вручную/
  ребутом в тот же сеанс).
- Воспроизведение: `kill -9` на xray-инстансе с xray-драйвером → остался ли
  `ifconfig xraytunN`? → `ifconfig xraytunN destroy` → старт. Затем —
  повторить с Lock ON/OFF и сравнить.

### Кандидаты на реализацию (отложенный план v4.4.1)

1. `tun_destroy()` — bool + ретраи 5×300мс (EBUSY, пока отпускают fd) + лог.
2. `do_start()` — предстартовая чистка stale-клонов: интерфейс существует →
   проверка владельца (pid-файлы других инстансов) → охота на осиротевшие
   xray-процессы (вне pid-файлов) → `tun_destroy()` с ретраями → при неудаче
   внятная ошибка «run: ifconfig <name> destroy» и отказ от старта.
3. `do_stop()` — guard владельца перед destroy (не убить живой интерфейс
   соседа при дубле имён).
4. Валидация дублей `tun_interface` между включёнными инстансами при Apply:
   громкая ошибка, конфликтующие не стартуют.
5. README: инструкция по assign — пересмотреть рекомендацию Lock (см. 4.4.1,
   сделано: помечен как «опционально, эмпирически мешает»).

### Связанное

- Отдельное upstream-решение (радикальное): патч xray на `TUNSTRANSIENT`
  ioctl — тогда клон умирает вместе с процессом автоматически. Требует
  правки xray-core, не плагина.
